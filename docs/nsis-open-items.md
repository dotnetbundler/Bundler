# NSIS external validation and open inputs

This file records work that cannot be honestly completed using repository-only fixtures. It is not a substitute for implementation work that can be automated locally.

| Item | Current reason | Input needed | Impact |
| --- | --- | --- | --- |
| Real Authenticode end-to-end signing | The built-in two-stage Authenticode pipeline is implemented and covered with a disposable self-signed certificate, but the repository has no production certificate/private key or public timestamp service contract. | Provide a production signing identity and RFC 3161 timestamp-service URL in a controlled release environment. | Local tests verify PE signing mechanics; public trust-chain, hardware/cloud signer, and timestamp-policy acceptance still require external credentials and infrastructure. |
| Production WiX migration | The configurable ProductCode/UpgradeCode migration pipeline is implemented, but no historical identifiers or released MSI fixture has been supplied. | Real legacy identifiers and representative x86/x64, current-user/per-machine MSI packages or registry exports. | Disposable fixtures verify the generic mechanism; recognition and privilege behavior of an actual released product remain unverified. |
| Elevated per-machine install/uninstall | Normal local tests must not silently trigger UAC. | An elevated Windows CI worker or an explicit manual test run. | Installer compilation and registry-routing logic can be automated without elevation; actual HKLM/Program Files writes need elevated validation. |
| Genuine reboot-required file deletion | Repository integration tests verify exit code `3010`, committed transaction state, journal cleanup, and launch suppression by setting the NSIS reboot flag, but they deliberately do not mutate the machine-wide pending rename queue. | Run `tests/Windows.Nsis.Reboot/Verify.ps1` in an elevated disposable Windows VM, reboot it, and run the verification phase. | The uninstaller reports `3010` when `/REBOOTOK` queues a locked-file deletion; actual queue execution and post-reboot cleanup remain external evidence. Locked-file replacement during install is intentionally not queued: delayed replacement requires elevation, cannot behave consistently for `currentUser`, and cannot be safely folded into the current rollback transaction. See `docs/nsis-locked-payload-policy.md`. |
| Start Menu/taskbar pin cleanup across Windows releases | Shortcut ownership checks and AppUserModelID metadata are implemented, but pin storage and supported unpin APIs differ across Windows versions and policies. | Manual validation on supported Windows 10/11 builds, including pinned-before-upgrade and pinned-before-uninstall cases. | The installer safely preserves foreign same-name shortcuts; automatic unpin is not currently claimed as guaranteed behavior. |
