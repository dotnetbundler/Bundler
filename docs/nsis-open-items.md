# NSIS external validation and open inputs

This file records work that cannot be honestly completed using repository-only fixtures. It is not a substitute for implementation work that can be automated locally.

Detailed prerequisites, commands, expected results, evidence fields, and cleanup steps are consolidated in `docs/manual-testing.md`. That document is the execution checklist for final manual acceptance; this table remains the short open-input index.

| Item | Current reason | Input needed | Impact |
| --- | --- | --- | --- |
| Real Authenticode end-to-end signing | The full staged payload/plugin/uninstaller/installer pipeline and external command provider are covered with disposable fixtures, but the repository has no production certificate, HSM/cloud account, or public timestamp-service contract. | Provide the production signing identity/provider and RFC 3161 policy in a controlled release environment. | Local tests verify ordering, isolation, PE signing, failure cleanup, provider invocation, and redaction; public trust-chain, hardware/cloud policy, timestamp acceptance, and SmartScreen reputation still require external infrastructure. |
| Production WiX migration | The configurable ProductCode/UpgradeCode migration pipeline is implemented, but no historical identifiers or released MSI fixture has been supplied. | Real legacy identifiers and representative x86/x64, current-user/per-machine MSI packages or registry exports. | Disposable fixtures verify the generic mechanism; recognition and privilege behavior of an actual released product remain unverified. |
| Elevated per-machine install/uninstall and journal ACL | Normal local tests must not silently trigger UAC. Current-user journal and HKCU integrity anchors are writable by that same user; this workstation did not have an elevated-created `%ProgramData%\DotNetBundler` directory from which to record final ACLs. A standard user may be able to pre-create a child under `%ProgramData%`; the actual ownership and inheritance must be checked, including the recovery uninstaller and registry anchors. | An elevated Windows CI worker or MT-01/MT-07 run recording owner, `icacls`, HKLM permissions, and the pre-created-parent case. | Local tests cover static payload/registry snapshot and recovery EXE tampering. They do not prove a hostile lower-privilege user cannot race or replace files in a per-machine journal; release acceptance requires the actual elevated ACL boundary. |
| Genuine reboot-required file deletion | Repository integration tests verify exit code `3010`, committed install state, journal cleanup, and launch suppression by setting the NSIS reboot flag, but they deliberately do not mutate the machine-wide pending rename queue. Forward-uninstall failure and interruption recovery are automated without reboot. | Run `tests/Windows.Nsis.Reboot/Verify.ps1` in an elevated disposable Windows VM, reboot it, and run the verification phase. | The script copies the uninstaller and uses `_?=` so it waits for the actual uninstall process rather than the NSIS self-copy launcher, then requires `3010` and a product-owned pending delete. Actual queue execution and post-reboot cleanup remain external evidence. Locked-file replacement during install is intentionally not queued: delayed replacement requires elevation, cannot behave consistently for `currentUser`, and cannot be safely folded into the install rollback transaction. See `docs/nsis-locked-payload-policy.md`. |
| Start Menu/taskbar pin cleanup across Windows releases | Shortcut ownership checks and AppUserModelID metadata are implemented, but pin storage and supported unpin APIs differ across Windows versions and policies. | Manual validation on supported Windows 10/11 builds, including pinned-before-upgrade and pinned-before-uninstall cases. | The installer safely preserves foreign same-name shortcuts; automatic unpin is not currently claimed as guaranteed behavior. |
| Real ACL denial and disk exhaustion | Deterministic fault injection covers transaction checkpoints, but it does not reproduce real NTFS/registry ACL denial or physical/quota exhaustion. | Disposable Windows VMs following MT-07, with narrowly scoped deny rules and a dedicated virtual disk or quota. | The product promises safe failure/recovery, not complete ACL/ADS metadata fidelity; real OS failure behavior remains external evidence. |
| Native host and Windows ARM64 matrix | Tool selection and packages cover Windows, Linux x64/arm64 and macOS x64/arm64 hosts plus Windows x64/arm64 targets, but this workstation cannot be evidence for every native host/target. | Native runners and Windows ARM64 hardware/VM following MT-08/09. | Repository tests verify selection, cache integrity and Windows x64 behavior; native execution claims remain bounded to tested environments. |
| Built-in localization content review | Automated tests validate the canonical key set, compile all 22 built-in languages, and run a non-Latin Windows install/uninstall fixture, but the newly supplied translations have not been reviewed by native speakers or professional localizers. | Native or professional review for every language, with Windows screenshots at representative display scales and focused RTL review for Arabic/Persian. | Structural correctness and Unicode transport are verified locally; linguistic accuracy, regional terminology, text truncation, and visual RTL quality remain external content acceptance (MT-11). |
